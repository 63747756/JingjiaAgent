## 计量和预留

私有节点元数据增加 `capacity_id = SHA256(Docker Engine ID)`。daemon 的持久
实例 ID 和连接指纹仍分别校验；同一 Docker Engine 上的不同 daemon 实例共享
一个容量池，不能因配置多个节点地址而重复计算宿主容量。

新增迁移 `000030_runtime_capacity`，增量增加节点池映射、容量池及环境预留表。
不重建业务数据表。CPU 用整数毫核、内存用字节记录，请求与实际 Docker 限制采用
同一转换：默认 2 CPU、8 GiB，CPU 最多三位小数，拒绝负数、非有限数、溢出及
超出支持范围的请求。Web 原有整数资源选择方式保持不变。

容量池预算为实际 Docker CPU/内存减去管理员预留，再受可选上限约束。这里的实际
宿主是 Docker Engine 所在机器；Docker Desktop 下为 Linux 虚拟机。预留是同一
业务数据库内按请求限额做的准入账本，不按瞬时 RSS 计量，不包含磁盘配额；其他
Docker 项目和使用其他数据库的平台实例需通过独立宿主或容量预算分配处理。

环境、预留及独立环境的准备命令在同一事务中提交。容量不足返回原业务错误流程，
不提交环境或 Run。任务分轮执行、重试、Worker 重建都复用环境的一条预留。
创建时先写入的待执行业务任务会标记为失败，临时模型凭证和未获准的 VM 从原查询
中移除，避免占用任务并发额度；提交超时等不确定结果不执行这项补偿。

## 生命周期

| 状态/操作 | 预留处理 |
| --- | --- |
| 准备、执行、任务完成 `KEEP_RUNNING` | 持有 |
| 休眠、恢复、节点离线、服务重启 | 持有，保证恢复资源 |
| 提交超时、未知 Run、回收响应丢失 | 持有，等待同一节点对账 |
| 失败/取消，确认从未提交且没有 Sandbox 或其他活动命令 | 与最终状态一起释放 |
| 确认 Sandbox 回收完成 | 与环境 tombstone 一起释放 |

回收先在数据库记录 `stopping`，阻止新的任务准入；休眠和恢复与回收通过同一
环境行锁串行处理。没有确认删除时保留 fence 和预留。没有 Sandbox 映射但存在
历史提交记录的环境不能被当作空环境回收。

p8 在所有删除阶段完成后，以原子写入、文件同步和目录同步保存私有回收记录，
再删除生命周期 journal。记录位于 daemon 持久卷的
`sandboxes/.monkeycode-recycled/`，只含版本、Sandbox ID 和完成标志。
再次删除时，只有生命周期记录及业务元数据确实缺失，且回收记录有效，才确认
原删除成功。损坏记录、I/O 故障或单纯缺失元数据仍然拒绝确认；同 ID 的新 Sandbox
元数据优先于旧回收记录。这些记录用于运行层对账，不保存或归档工作区文件。

## 配置与启用

```yaml
runtime:
  capacity:
    enabled: true
    reserve_cpu_millis: 2000
    reserve_memory_bytes: 4294967296
    max_cpu_millis: 0
    max_memory_bytes: 0
```

示例给宿主留 2 CPU、4 GiB；`max_*: 0` 表示使用减去预留后的实际容量。
启用前完成以下顺序：

1. 所有业务后端/Worker 升级到支持迁移 30 和预留的版本，暂保持 `enabled: false`。
   不允许旧版写入进程继续连接已启用容量控制的数据库。
2. 升级相应 daemon 至 p8，并确认所有在线节点及非回收环境所属节点都已采集
   `capacity_id`。先绑定身份，再通过单独事务启用预算；缺失的旧节点映射会阻止
   启用，确认结果会保留，供后续心跳补齐。
3. 设置预算并启用。通过数据库共享/独占事务锁串行化节点映射变更、旧环境补账
   和准入，不让启用期间的请求漏记。正常请求再用池行锁计算总预留，防止并发超额。
4. 旧环境按原请求补账，已经超过预算的环境继续持有资源，新请求拒绝；不会为
   达到预算自动删除、迁移或重放旧环境。

预算一旦在池中启用，其他升级后的进程即使配置 `enabled: false` 也不能绕过。
心跳只能收紧预算，不能自动提高或关闭。缩减预算不会驱逐已有环境。扩大预算应
先统一所有后端配置，再由运维在确认实际宿主资源后，事务锁定目标池并调整
`cpu_limit_millis` / `memory_limit_bytes`，不能清空预留表或禁用池来恢复容量。
当前没有新增管理员容量管理页面。

业务接口沿用原错误封装与中英文本：容量不足 `409/10237`，容量未确认或预留已
释放 `503/10238`，资源参数无效 `400/10239`。这里只描述错误契约；本轮未把真实
Web 页面上的容量不足操作算作验收。

## 验证与复现

```powershell
python runtime/agent-compose/build.py --no-prepare
$env:RUNTIME_TEST_DATABASE_URL = 'postgres://postgres:runtime-test-only@127.0.0.1:44458/runtime_test?sslmode=disable'
python runtime/agent-compose/run_capacity_live.py
```

`--no-prepare` 只构建版本化镜像，不覆盖已部署的 `.state/images.json` 和 Compose
配置。容量测试另外保存 `.state/capacity-images.json`，启动
`jingjia-runtime-capacity-a/b` 两个独立 Compose 项目，监听回环 47414/47415。
测试清理本轮创建的 Sandbox 和临时 schema，保留两个 daemon 的身份卷；不操作
原 Web、原安装节点或其他 Docker 项目。测试预算为 1 CPU、2 GiB，不是生产配置。

数据库测试覆盖 24 个并发请求跨两个别名共享预算、完整回滚、精确重试、禁用配置
进程不可绕过、旧环境补账、升级门槛、任务事务回滚、状态持有、失败证明及回收释放。
真实测试覆盖两个独立 daemon 身份、相同实际宿主容量池、实际 cgroup 限制、准备
完成/休眠/恢复、Worker 重建，以及实际删除成功但响应丢失后的保留和释放。
准备 Run 执行 `true`，不调用模型；此结果不替代真实 Agent 故障验收和生产容量评估。

## 回退边界

新增环境路由仍按原发布规则回退，已提交环境继续使用固定后端和节点。
回退不能跨后端重放任务，也不能退回不认识预留表的旧业务写入程序。
保留迁移 30、预留记录和 p8 回收记录。数据库 down 文件仅用于无运行环境的隔离
测试，不用于正在管理 Sandbox 的业务库。
